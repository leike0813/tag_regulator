## Context

当前发布包目录 `tag-regulator/` 内的核心文档（`SKILL.md`、`README.md`）以英文为主，但本项目的使用与维护语境以中文为主。由于该项目是 **Agent Skill**（提示信息与指导本身就是“实现主体”），文档的清晰度与一致性直接决定运行质量与契约遵守程度。

本次变更为纯文档中文化与语言规范化：
- 只处理发布包内**文本文档**：`tag-regulator/SKILL.md`、`tag-regulator/README.md`
- 不改动脚本、schema、测试等非文档内容
- 不引入任何行为变化：翻译必须语义等价

## Goals / Non-Goals

**Goals:**
- 将 `tag-regulator/SKILL.md` 与 `tag-regulator/README.md` 完整中文化，同时保持技术细节与约束不变。
- 建立明确的语言规范：后续发布包内文本文档改动以中文为准。
- 保持所有代码标识符与数据契约原样（字段名、键名、路径、命令行、示例 JSON 结构等），避免引入不兼容。

**Non-Goals:**
- 不对脚本/Schema/测试进行中文化改写（除非后续明确要求）。
- 不重写或优化原有内容结构（除必要的翻译与少量措辞调整以提升中文可读性）。
- 不引入新的功能、默认行为或输出字段。

## Decisions

1) **翻译范围只覆盖发布包内文本文档**

Rationale：发布包对外的“可用性”主要由 `SKILL.md`/`README.md` 决定；而脚本与 schema 属于实现/校验层，不应为了语言而改变可执行内容或接口。

2) **保持契约/标识符“逐字不变”**

具体约束：
- YAML frontmatter 的 `name` 不改；`description`/`compatibility` 允许中文化，但其中的 `$tag-regulator`、字段名（`valid_tags` 等）保持原样。
- 所有 JSON 示例中的键名、字段名、路径与命令行示例保持原样。
- 代码块内不做“翻译式改写”（只翻译代码块外的说明性文本）。

Alternative：将示例 JSON 里的提示字符串也完全中文化。可能引入误导（如把字段名翻译掉），因此仅在不影响契约的前提下翻译自然语言内容。

3) **“后续改动都以中文进行”的落点**

采用“文档规范”方式落地：
- 在 `SKILL.md`/`README.md` 中明确声明：发布包内文本文档以中文为准，后续修改请优先用中文撰写。
- 不强制要求仓库级所有内容都中文化，以免影响工具链与代码可读性。

## Risks / Trade-offs

- [翻译导致语义漂移] → Mitigation：逐段对照翻译，保留技术术语与约束用词（MUST/SHALL 等）对应中文强制措辞（必须/应当），并避免改动结构与列表含义。
- [误翻字段名/路径/命令导致不兼容] → Mitigation：对所有代码块与内联 `code` 保持原样，仅翻译解释文本。
- [未来贡献者继续用英文改动] → Mitigation：在两个文档中增加清晰的“语言规范”段落，并在 OpenSpec 任务中加入检查项。
